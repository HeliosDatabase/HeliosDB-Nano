# A14 Result - Transaction Error State Recovery

## Verdict

Positive. Commit eligible.

The regression is present before the fix: an error response inside an open PG-wire transaction leaves the embedded database transaction active. The next `BEGIN` is then rejected by storage with `Transaction already active`, even though the client has already received an error response and should be able to start a fresh transaction for this checklist item.

## Scope

- Source: `src/protocol/postgres/handler.rs`
- Source: `src/protocol/postgres/handler_extended.rs`
- Regression: `tests/a14_postgres_transaction_error_recovery.rs`
- No planner, executor, storage engine, or unrelated protocol files changed.

## Fix

- Error responses now mark an open transaction as `Failed` without rolling it back immediately.
- `BEGIN` performs the A14 recovery: if protocol state is `Failed`, it rolls back the aborted embedded transaction first, resets state to `Idle`, then starts a fresh transaction.
- `ROLLBACK` and `COMMIT` also clear failed transaction state by rolling back the embedded transaction when one is present.
- This preserves PostgreSQL-style `25P02` failed-transaction behavior for ordinary statements between the error and a recovery command.
- Ported Claude's extended-protocol transaction-control fix:
  - `BEGIN`, `START TRANSACTION`, `COMMIT`, and `ROLLBACK` in extended Execute now route through `handle_single_query()`.
  - `ReadyForQuery` remains suppressed for that internal call so extended protocol still emits RFQ only after `Sync`.
  - This keeps handler `TransactionStatus` synchronized with the embedded database transaction for extended clients.
- Added an extended-protocol failed-transaction guard so non-transaction-control extended statements return `25P02` instead of executing while the transaction is aborted.
