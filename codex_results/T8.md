# T8 Result - GROUP-BY-without-aggregate MV does not dedupe rows

## Verdict

REAL BUG - fixed. The root cause is broader than materialized views: the general
planner dropped `GROUP BY` whenever the SELECT list had no aggregate functions.
Materialized views inherited the wrong rows because their defining query already
returned duplicates.

Baseline: branch `fix/codex-v334-t8` from consolidated final `main` at `51591d2`
(A8+A14+A15+A5+A1+A7+T2+T3).

## Baseline

`cargo test --test v334_t8_mv_group_by_dedup -- --nocapture`: FAIL, 0/4.

Observed failures before the fix:

- Direct `SELECT a, b FROM t8_pairs WHERE tenant = 100 GROUP BY a, b` returned
  5 rows instead of the 3 distinct `(a,b)` groups.
- `CREATE MATERIALIZED VIEW ... SELECT a, b ... GROUP BY a, b` stored those same
  5 duplicate rows.
- `REFRESH MATERIALIZED VIEW` preserved 7 rows after adding one duplicate group
  and one new group, instead of 4 groups.
- A 300-row stress MV stored all 300 base rows instead of 30 group rows.

## Root Cause

`src/sql/planner.rs` only constructed `LogicalPlan::Aggregate` when
`has_aggregates` was true. For `GROUP BY` without aggregate functions,
`has_aggregates` was false, so planning fell into the ordinary projection path
and silently ignored the group keys.

The executor already supports grouped aggregation with an empty aggregate list:
the grouped operator emits one tuple per group key. The missing piece was routing
these queries into that aggregate path.

## Fix

Changed `select_to_plan` to treat non-empty `GROUP BY` as an aggregate query even
when `aggr_exprs` is empty:

- `if has_aggregates || has_group_by`
- keep existing group-expression and ordinal resolution.
- keep the existing post-aggregate projection rewrite.

This is deliberately not implemented as a blanket `DISTINCT` over the final
projection. `SELECT a FROM t GROUP BY a, b` must emit one row per `(a,b)` group,
which can contain repeated `a` values. The regression test locks that behavior.

Production diff: `src/sql/planner.rs`, +12 / -1.

## Regression

`tests/v334_t8_mv_group_by_dedup.rs` covers:

- Direct `GROUP BY` without aggregates matches `SELECT DISTINCT a,b` for the
  projected group keys.
- `SELECT a FROM ... GROUP BY a,b` returns one row per group key, not distinct
  projected `a` values.
- MV creation stores deduped group rows.
- `REFRESH MATERIALIZED VIEW` re-materializes deduped group rows after
  parameterized inserts.
- Bounded 300-row stress smoke groups 300 input rows into 30 MV rows.

## Performance

Targeted stress after fix:

- `CREATE MATERIALIZED VIEW ... SELECT a,b FROM 300 rows GROUP BY a,b` grouped
  the data into 30 MV rows in `11.180391ms` on the final run.

Baseline stored 300 incorrect MV rows for that workload. The fix may add the
expected grouping hash map for this query class, but it removes duplicate
materialization work and brings the plan in line with SQL semantics.
