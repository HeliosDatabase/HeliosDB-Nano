# T2 Result - COUNT(*) over a materialized view returns 0

## Verdict

REAL BUG - fixed.

Baseline: branch `fix/codex-v334-t2` from consolidated final `main` at `65b3629`
(A8+A14+A15+A5+A1+A7).

## Root Cause

The unfiltered `COUNT(*)` fast path in `src/sql/executor/mod.rs` passed the
user-visible materialized-view name to `storage.count_table_rows`. MV rows are
stored in the backing table named `__mv_<name>`, so the fast path counted
`data:<mv>:` keys and returned 0. Direct row reads and `SUM(1)` already go
through the scan path, which resolves MV names to backing tables.

Claude's comparison point also exposed the same bug shape in more storage-level
aggregate fast paths: `COUNT(id)` over the MV still returned 0 after fixing only
the direct `count_table_rows` call sites because row-store aggregate pushdown also
scanned the logical MV name.

## Fix

Added `Executor::fast_path_storage_table_name`, mirroring the scan path's MV
resolution:

- Non-MV tables pass through unchanged.
- MV names resolve to `MaterializedViewCatalog::mv_data_table_name(name)`.
- Missing MV backing tables return the existing "never been refreshed" error
  instead of silently treating catalog errors as non-MVs.

Applied the resolver at all storage fast paths touched by this surface:

- `COUNT(*)` no-predicate fast path.
- Single-PK count cardinality no-predicate path.
- Columnar aggregate pushdown.
- Row-store aggregate pushdown.

Production diff: `src/sql/executor/mod.rs`, +29 / -4.
