# A5 Result - CHECK Constraints On Parameterized Writes

## Verdict

Positive. Commit eligible.

The checklist item is still present on the consolidated baseline `49cbd39`, but only on the parameterized DML executor. The simple `execute()` INSERT/UPDATE path already enforced CHECK constraints, and the fast-path builders correctly decline tables with CHECK constraints. The fallback `execute_plan_with_params()` INSERT, UPDATE, INSERT SELECT, and ON CONFLICT DO UPDATE branches were missing the same CHECK validation call.

- Source: `src/lib.rs`
- Regression: `tests/v334_a5_check_constraints.rs`
- No parser, catalog, storage, protocol, or transaction-state changes.

## Fix

- Added a small `validate_check_constraints()` helper around the existing `evaluate_check_constraint()` implementation.
- Called it from the parameterized DML branches before storage writes:
  - INSERT
  - INSERT SELECT
  - ON CONFLICT DO UPDATE after applying update assignments
  - UPDATE after applying assignments and FK validation
- Kept the existing fast-path exclusion design: tables with CHECK constraints still route away from fast DML builders.

## After

- Result after fix: PASS, 4 passed / 0 failed.

  - compliant rows are accepted.
  - inline and table-level CHECK violations are rejected on parameterized INSERT and UPDATE.
  - INSERT SELECT rejects CHECK-violating source rows.
  - ON CONFLICT DO UPDATE rejects a final updated tuple that violates CHECK.
  - no CHECK-violating rows leak through the tested paths.
