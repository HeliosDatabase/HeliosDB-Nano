# Physical standby replication: 1:1 replica, WAL-level, read-only serving

**Status:** APPROVED PLAN (maintainer, 2026-10-20), pending the open points in §"Open points". No code yet.
Supersedes the physical-vs-logical question in `STANDBY_RECOVERY_PLAN.md` §4. Branch `fix/replication-retention-j`.


## Context

Field finding J (Sprinter `58d4e3113e56`) showed the HA pair is operationally fragile: the
logical standby exits on refusal, has no rebuild path, and the logical WAL has known coverage
gaps (embedded explicit transactions, some DDL orderings). The maintainer's direction
(2026-10-19, Oracle background): redefine WAL replication so a standby is a **1:1 physical
replica** of the primary (Oracle physical standby for read-only replicas), read-only for users
while the replication applier and database-owned processes may write; WAL retained up to disk
capacity or a user parameter (default 7 days) with rotating WAL files; "fireproof": everything
replicated at WAL level, so a standby can be built/advanced **from the primary or from WAL**.

Decisions already taken (this session):
- Disk pressure: **prune oldest retained WAL, never stall** primary writes (reserve + WARN + status).
- **Physical replaces logical** for all standbys; native v3 channel becomes control plane only.
- Standby **stays up** on refusal (J2); recovery window default **7d**; rebuild modes "from
  primary" (incremental fast-forward, `dafb3894ef87`) and "from WAL" (archive + catalog,
  `e619d47c3457`). Existing plan: `docs/plans/STANDBY_RECOVERY_PLAN.md` (pushed, `44e67d1f`).

Branch: `fix/replication-retention-j` in `/home/gpc/HDB/worktrees/nano-4411-integration`
(J1 retention window + J1a cancel-safe transport, gated, pushed). This plan supersedes the
"physical vs logical" question in STANDBY_RECOVERY_PLAN.md §4 with the physical decision and

## Design

### D1. Architecture in one paragraph
One RocksDB WAL is the single source of truth. The primary's write groups (one WAL record each) are the unit of replication; a standby applies them verbatim into its own RocksDB, so its replicated keyspace at cursor `T` is byte-identical to the primary's at sequence `T`. Node-local state lives in a separate column family and never touches the replicated keyspace. The standby serves read-only SQL from the same RocksDB through a `StorageEngine` opened in a new `PhysicalStandby` mode that performs no writes of its own; the applier keeps the engine's in-memory derived structures (ART, HNSW, time-travel snapshot map, caches) current from the keys in each applied batch. WAL records are also sealed into rotating **archive segment files** on the primary (and optionally on each standby); the recovery window (default 7 days, bounded by disk) is enforced on those segments, never by stalling the primary. A standby can therefore be advanced from the primary (stream) or from WAL (segments), and rebuilt by a resumable checkpoint copy or an incremental fast-forward. The native v3 channel is reduced to a control plane (handshake, history/epoch, heartbeats, physical-sequence ACKs, fencing).

### D2. Keyspace classes and byte-identity
| Class | Examples | On a standby |
|---|---|---|
| Replicated (default CF) | `data:`, `v:`, `v_idx:`, `snapshot:`, `vmeta:`, `meta:*`, `counter:`, `table_constraints:`, `trigger:`, `__vidx:`, `idxsnap*`, `vecsnap*`, `col*`, `cas:`, `dict:`, `delta:`, `branch:*`, `bdata:`, `bdel:`, `bv:`, `wal:*`, `vgc:*`, `w3_2_elide_used`, `meta:tde:keycheck` | written ONLY by the applier, verbatim |
| Node-local (new CF `local`) | applier cursor, standby posture/state, archive catalog, per-node stats | written only through `StorageEngine::write_local` |
| Forbidden on a standby | user DML/DDL, sequences, snapshot registration from read-only COMMIT, GC, close-time persistence | refused / suppressed |

Rules: (1) a source-scan CI test lists every key prefix written in `src/` and fails if one is unclassified (same device as the cut-marker writer test in `REPLICATION_4_41_1_DESIGN.md` §3.1); (2) a range-digest test proves replicated ranges are identical between a primary checkpoint at `T` and a standby at cursor `T`; (3) `repl:applied_lsn` and `__nano_physical_replica_cursor_v1` move to the `local` CF (no more cursor put inside replicated batches, physical.rs:415-431). The existing poison tripwire (physical.rs:329-331, 396-399) stays, generalised: `latest_sequence_number` may only advance through the applier or `write_local`.

### D3. Serving physical standby — the core
Two crate facts shape it (verified): `rocksdb::DB = DBWithThreadMode<SingleThreaded>` (`create_cf` takes `&mut DB`: create the CF before wrapping in `Arc`; `DB::list_cf`, `open_cf_descriptors`, `cf_handle` exist); `WriteBatchIterator` drops range-deletes and CF ids, so the applier decodes raw bytes itself (`validate_raw_batch`, physical.rs:119-172, already does).

**D3.1 Node-local namespace = column family `__nano_local`.** Cursor, posture, archive catalog, stats live there; the default CF stays a byte-for-byte copy of the primary's. CF writes draw from the same sequence counter, so the existing accounting (`local_operations = last-first+2`, physical.rs:417) is unchanged with the `+1` now a `put_cf(local, cursor)`. **Every** write on a standby — applier or owned — goes through one `LocalWriter { db: Arc<DB>, cursor: Mutex<PhysicalCursor>, poisoned }` with `apply_source(&PhysicalBatch)` (today's `StagedPhysicalReplica::apply`) and `write_local(LocalBatch)` (cursor `local_sequence += len+1`, fsync). `LocalBatch` can only address the local CF. `StagedPhysicalReplica.db: DB` → `Arc<DB>` + `Arc<LocalWriter>` (physical.rs:337-341). The poison invariant `latest_sequence_number == cursor.local_sequence` (physical.rs:329, 396) stays checkable after every write. Export's "receiver cannot be a source" check (physical.rs:222) becomes "`list_cf` contains `__nano_local`"; a receiver's own WAL (CF opcodes) is refused by `validate_raw_batch` → cascading is fail-closed until R3 strips local records. No CF on a primary in v1. A v1 staging dir (cursor in default CF) → typed `FullResyncRequired` (no production physical standbys exist).

- Consistent cut: one `PhysicalBatch` = one write group; publishing per batch under the lock shows exactly a primary crash-recovery state at that sequence → **cut markers deferred** (DROP TABLE meta-delete then data-delete resolves as "table gone"; ADD COLUMN resolves via rebuild). - Single-threaded applier; one fsynced write per batch (vs one per row on the logical path, 11646-11650); fsync may be amortised per poll (ties to `durable` ACK). Estimate 50-100k rows/s — measure.

**D3.5 Serving handle = (A) one writable `Arc<DB>` shared by applier and engine.** (B) `open_as_secondary` duplicates cache/memtables, cannot write the local CF, still needs D3.4, `get_updates_since` on a secondary unverified; (C) checkpoint+reopen per generation costs O(rows) ART/HNSW rebuild per publication. Construction in `start --replication-role standby` (main.rs:3318-3475): keep `prepare_receiver_history`; replace writable `with_config` (1862) by: no marker → bootstrap `run_receiver(InstallOnce)` (physical_receiver.rs:556) from the primary (legacy logical dir refused with the conversion note); `ReopenedPhysicalStage::open`/`CheckpointOpen::open` (checkpoint_transfer.rs:947-967, 770-795) use one `StorageEngine::build_db_options(&Config) -> (Options, Vec<ColumnFamilyDescriptor>)` factored from engine.rs:2529-2600 and `open_cf_descriptors`; `StorageEngine::open_physical_standby(path, cfg, db, writer)` → `EmbeddedDatabase::with_physical_standby` (variant of `with_config_open_policy` lib.rs:10527-10575 taking the strict rebuild branch catalog.rs:561; no `MVScheduler`); receiver worker `Command::Apply` → `PhysicalApplier::apply`; `run_receiver(Follow)` replaces `WalApplicator`+forwarder (3366-3408). **Posture** (`src/replication/standby_posture.rs`): `enum StandbyPosture {Connecting, CatchingUp{cursor,barrier}, Streaming{cursor}, Reconnecting{since,cursor}, NeedsRecovery{reason,position,since}, Recovering{mode,progress}}` in a `watch`, derived from `ReceiverStatus` (physical_receiver.rs:127-162) with the connect barrier from `SourceSessionInfo::Resume{durable_barrier}` (490-497); `/ready` route next to `/health` (main.rs:3511-3529): 200 in streaming or reconnecting within `max_standby_lag`; `reject_guarded_standby_statement` consults the posture (55000 for data reads outside streaming/reconnecting); failure `select!` (2394-2422) no longer exits on refusal.

**D3.6 ACK identity on the physical sequence.** Primary captures `seq = db.latest_sequence_number()` right after its data write (transaction.rs:1678-1680, wal.rs:1064-1065; conservative upper bound) and `wait_replicated_sequence(seq)` replaces `wait_replicated(lsn)` (wal.rs:831-849; the logical LSN is inside the same batch, wal.rs:869-881). Standby: applier publishes `(source_sequence, durable)` into `AckState` after apply+publish; `StreamingClient` sends `Applied` on notify (today `Received` before apply, streaming.rs:1391/1413); `report_applied/report_flushed` (1517-1523) get callers. Primary: `StandbyInfo` (ha_state.rs:117-129) gains `applied_seq, durable_seq, history` with `fetch_max` (fixes the heartbeat regression at streaming.rs:718-725). `wait_for_sync` (ha_state.rs:488-532): SemiSync = `count(durable_seq>=seq && history==ours) >= min_acks`; Sync = `count(applied_seq>=seq) >= min_acks`. Config: `min_acks=1`, `sync_timeout_ms=10000`, `sync_timeout_action = warn|fail` (default warn; `fail` errors a locally durable commit — document like PG's cancelled synchronous commit).

**Invariants asserted in tests:** (1) byte identity: `range_digest(db, cf, prefix)` (SHA-256 over sorted `len(k)||k||len(v)||v`) of the ENTIRE default CF equal between a primary checkpoint at `T` and a standby at `cursor.source_sequence == T`; (2) `latest_sequence_number == cursor.local_sequence` after every write and across close/reopen, default-CF digest changes only across `apply_source`; (3) SQL subset: every standby row exists in the primary checkpoint at `T`; `COUNT(*)`, kNN, `AS OF` match; (4) posture: `/ready` 200 iff cursor ≥ connect barrier; poisoned writer → `needs_recovery`, process alive, 55000.

### D4. WAL retention: rotating archive segments, recovery window, disk capacity
- **Why segments and not RocksDB `archive/`:** RocksDB's TTL is a coarse per-file timer (max 1 day in our config, no catalog, not shippable); we need operator-visible, cataloguable, sealed files. The primary runs an **archiver** task: a local tailer over `get_updates_since` (reuse `poll_source`, physical.rs:217-274) that appends `PhysicalBatch` frames (history, first, last, digest, raw — physical_wire.rs:615-621) to the current segment and rolls it at `segment_max_bytes` (default 64 MiB) or `segment_max_secs` (default 300 s). RocksDB's own `set_wal_ttl_seconds` is kept only to cover archiver lag (default 1 h, lifted cap).
- **Segment file** `<archive_dir>/<history>/<epoch>/<first:020>-<last:020>.hseg`: header {format, history_id, epoch, first_sequence, created_at, node_id, key_check_id}, body = frames, footer {last_sequence, batch_count, first/last commit wall time, file SHA-256}. Sealed with the dataset key when encryption is on (keys inside batches are plaintext); mode 0600. Names sort in sequence order, so a directory is self-cataloguing.
- **Catalog** in the `local` CF: `arch:seg:{history}:{epoch}:{first:020}` → {path, last, bytes, sha256, times, state available|missing|corrupt|expired, source}. Rebuildable by rescanning files. Views `heliosdb_archived_wal`, `heliosdb_archive_gaps`; CLI `heliosdb-nano archive list|catalog --start-with DIR|verify [--deep]|gaps --from POS|prune`.
- **Retention policy** (`[replication]`): `recovery_window = "7d"` (parse with `parse_retention_duration_secs`, config.rs:904); `archive_max_bytes` (new byte-size parser `parse_byte_size("16GiB")`, default `"unlimited"` = disk capacity); `archive_disk_reserve` (default `"10%"`, also accepts bytes). **Pruning order:** expired beyond window → oldest first while over `archive_max_bytes` → oldest first while free space < reserve. **Never stall** primary writes (maintainer decision): when pruning shortens the effective window, WARN once per shortening and expose `effective_window`, `oldest_retained_at`, `bytes_retained` in `heliosdb_recovery_window`. Never prune a segment that a registered standby (per-standby cursor from ACKs, D3) still needs *while it is inside the window* — beyond the window the standby is refused into `needs_recovery`.
- **Disk measurement:** replace the `df` shell-out (`check_disk_space`, engine.rs:2142-2172) with `libc::statvfs` (libc already a dependency) in one `storage::disk::free_bytes(path)`; reuse it for the engine's 100 MiB check and for the archiver. Archiver and applier both call it (today the physical apply path never checks disk).
- **Logical WAL window (J1)**: `logical_wal_retention_entries` stays only as the primary's redo/catch-up window for the *transition period*; once standbys are physical it is no longer the standby's history source. Keep J1's floor semantics; default can drop later (open point for the review).

### D5. "Fireproof": closing the replication holes
Everything the primary persists must be reachable through the RocksDB WAL.
- `hnsw_snapshots/*.hnsw.{graph,data}` (engine.rs:9867-9957): derived data, but today standard-hnsw hydration prefers the file. Step 1: the standby ignores files and rebuilds from rows/`__vidx:` (what `rebuild_all_indexes_for_physical_snapshot` already does); step 2: store the graph dump as chunked RocksDB keys (`vecsnapc:{index}:{n}`) so it replicates and the file goes away; add the dump hash to the `vecsnap:` sidecar (index_snapshot.rs:161-177) in the meantime.
- Lock-free ingestion (`enable_lockfree_ingestion`, engine.rs:3675): writes reach RocksDB but bypass logical WAL/MVCC/indexes; refuse enabling it when `role=primary` (no callers exist today).
- `WalStore` dir `replication_wal/` (dead): remove creation (main.rs:3238-3256).
- `TenantManager` memory-only (tenant/mod.rs:842-856): pre-existing, not durable on the primary either — out of scope, documented.
- `shutdown_dump.heliodump` must not be written into a replica dir (`--dump-on-shutdown` refused on a standby).
- Encryption: a standby needs the same key (ciphertext is shipped verbatim); key rotation re-encrypts through RocksDB (replicates) but the standby must hold both keys during rotation → refuse `rotate` while any standby is attached without the new key (control-plane capability flag).

### D6. Recovery modes (from `STANDBY_RECOVERY_PLAN.md`, now physical-only)
- **From the primary:** ladder = tail (primary's archive/segments cover `S+1…`) → incremental fast-forward (same history, valid cursor, position older than history: leaf digests over the replicated keyspace at a pinned snapshot, differing leaves shipped as SSTs via `SstFileWriter`, applied with `delete_range` + `ingest_external_file`, crash-resumable under a `local` recovery record) → full copy (resumable checkpoint transfer). Sprinter `dafb3894ef87`.
- **From WAL:** `standby recover --from-archive [DIR…]` builds the chain from `S+1`, verifies header/footer/SHA-256 before applying anything, applies through the same applier (so derived state is maintained identically), then continues from the primary if reachable or stays `needs_recovery` naming the exact gap. The standby may also run **archive-only** (no primary connection; Oracle managed recovery from archived logs) with `--source archive`. Sprinter `e619d47c3457`.
- **Standby posture (J2):** states connecting / catching_up / streaming / reconnecting / needs_recovery / recovering; stays up; data reads refused with SQLSTATE 55000 in `needs_recovery`; `/ready` 503 until the barrier; `on_unrecoverable = stay-up|exit`; fix the unbound-directory trap (bind on the authenticated handshake's history before catch-up is planned, streaming.rs:1276-1281).

### D7. Control plane and transport
- **One replication connection** (recommended): NPHYS v2 carries data frames and the control frames (Hello{history, epoch, cursor, capabilities}, Heartbeat, Ack{applied_sequence, durable}, Fence). The native v3 listener remains for one release for logical standbys in transition, then is removed. Alternative: keep two listeners (5433 control / 5440 data); more surface, no benefit once logical is gone.
- **Remote + TLS:** lift loopback-only (physical_wire.rs:489-494, 936-944; main.rs:5224, 5305; physical_receiver.rs:79-89; config.rs:3250-3256). TLS via existing `tls_provider.rs` (`load_cert_and_key`, `load_ca_certs`) and `postgres/ssl.rs::load_tls_config` (client-cert verification → mTLS option); bearer token stays as the second factor; plaintext remote still refused unless `allow_insecure_remote`.
- **Resumable snapshot:** per-file offset resume in `checkpoint_transfer.rs` (files are SHA-256 verified already); remove the "fresh resync requires absent destination" rule only for a verified partial staging dir.
- **Cascading:** allow a standby to be an archive/stream source (today refused: export refuses a dir with a standby/physical marker, checkpoint_transfer.rs:348-363). Phase-gated.
- **Promotion (epoch):** durable `epoch` in the replicated keyspace (`repl:epoch` written by the promoting node as its first write), carried in every segment header and Hello; stale-epoch sources refused. Full fencing design stays `REPLICATION_4_41_1_DESIGN.md` §3.4.
