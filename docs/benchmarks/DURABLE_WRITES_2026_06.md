# Durable Writes Gauntlet — HeliosDB-Nano vs SQLite, June 2026

Write throughput at **honest durability tiers**. Generated by
`benches/public/run_durable_writes.sh`; every number was measured on the host
below (two full runs, 2026-06-11 — both reported where they differ).
Numbers are only comparable WITHIN a tier; comparing across tiers is the
dishonest-multiplier trap this document exists to avoid.

- Engine commit: `e129247` (v3.48.0 integration merge)
- Host: AMD EPYC 7371 16-Core (32 logical cores), 126 GiB RAM, el9,
  xfs on md-RAID. Measured fsync on this array: ~16-120 ms and **highly
  variable between runs** — single-writer Tier-1 numbers below inherit that
  variance; the multi-session scaling trend is the robust signal.
- N=10,000 rows / M=500 single-op statements; SQLite 3.34.1 (stdlib).

## Tier definitions

| Tier | Guarantee | Nano config | SQLite config |
|---|---|---|---|
| 1 | power-loss durable, fsync per commit | disk, `durable_commit=true`, explicit txn commits | `journal_mode=DELETE, synchronous=FULL` |
| 2 | WAL'd, process-crash durable; recent commits may be lost on power loss | disk default (`wal_enabled`, `wal_sync_mode=Sync`, `durable_commit=false`) | `journal_mode=WAL, synchronous=NORMAL` |
| 3 | none (CPU path reference) | in-memory | `:memory:` — see SQLITE_MIRROR_2026_06.md |

## Tier 1 — power-loss durable

Single-writer comparable pair: Nano `BEGIN;INSERT;COMMIT` cycles
(`run_durable_commit_bench`, durable=true) vs SQLite autocommit INSERT under
synchronous=FULL (each statement is a durable commit).

| writer(s) | Nano durable txn commits (txn/s), run A / run B | SQLite FULL (ops/s), run A / run B |
|---|---:|---:|
| 1 | 63 / 8 | insert 23 / 19, update 23 / 20, delete 22 / 19 |
| 8 sessions | 140 / 26 | n/a — single writer |
| 16 sessions | 217 / 222 | n/a |
| 24 sessions | 309 / 381 | n/a |
| 32 sessions | **392 / 391** | n/a |

Honest reading:

- At ONE writer both engines are fsync-bound and within the same order of
  magnitude: Nano measured 0.4x-3.3x SQLite across the two runs on this
  high-variance array. No 100x headline exists at this tier — as predicted
  in the roadmap's tier-disclosure warning.
- The durable win is **concurrency**: RocksDB group commit amortizes the
  fsync, scaling to ~390 durable txn/s at 32 sessions — ~17-20x SQLite,
  whose writes serialize. This is the honest multi-client headline.
- Bulk loads amortize Tier-1 cost on both engines: a single 10k-row
  transaction ran at 115,529 ops/s (Nano, durable_commit=on) and
  96,338 ops/s (SQLite FULL) — one fsync per transaction, not per row.

### Known gap: autocommit statements do not honor `durable_commit`

Verified by the script's "tier1_probe": the suite's autocommit
INSERT/UPDATE/DELETE rates are statistically identical with
`durable_commit=true` vs `false` (e.g. autocommit_insert 65,267 vs
73,287 ops/s; ~60k ops/s is physically impossible on a ~16ms-fsync array if
each op fsynced). The autocommit fast path (`try_autocommit_fast_insert`,
src/lib.rs:5086) bypasses the sync-commit transaction that
`begin_autocommit_transaction` configures (src/storage/engine.rs:2862).
**Consequence: with durable_commit=true, only explicit transaction commits
are power-loss durable today.** Until fixed, Tier-1 claims must use the
explicit-transaction shape, as this document does. (Follow-up engine issue;
the probe in `run_durable_writes.sh` keeps the gap visible.)

## Tier 2 — WAL'd, process-crash durable (run B; run A within ±10%)

| workload | Nano disk default (ops/s) | SQLite WAL/NORMAL (ops/s) | Nano / SQLite |
|---|---:|---:|---:|
| bulk_insert_users(txn) | 160,127 | 138,459 | **1.16x** |
| autocommit_insert | 73,287 | 33,291 | **2.20x** |
| update_by_pk | 64,406 | 4,180 | **15.41x** † |
| delete_by_pk | 152,546 | 40,099 | **3.80x** |

† SQLite's WAL update number includes checkpoint stalls; its FULL-mode
update is ~20 ops/s, so the comparison stands but the exact multiple is
noisy.

## Repro

```bash
benches/public/run_durable_writes.sh        # honest tiers, raw logs, results.json
```

The script refuses to fake durability: if `$TMPDIR` is tmpfs (RAM), it
relocates the databases to a real-disk path and says so.
