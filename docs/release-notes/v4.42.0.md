# HeliosDB-Nano 4.42.0 release notes

HeliosDB-Nano 4.42.0, released on 2026-11-20, makes every SQL statement atomic, replaces
replication with physical standbys that can be verified, promoted online and switched over, and
turns a branch into a fork that each session selects for itself. It fixes lost updates under
concurrency and wrong `AS OF` results, and it publishes a reproducible benchmark against
HeliosDB-Nano 4.41.1 and PostgreSQL 18.4, including the results that got slower.

HeliosDB-Nano is an Apache-2.0 embedded ACID database in a single binary. It speaks the PostgreSQL
and MySQL wire protocols and includes vector search, database branching and time-travel (`AS OF`)
queries.

## What is new in HeliosDB-Nano 4.42.0?

- **Every statement is atomic.** A schema statement such as a multi-clause `ALTER TABLE`,
  `CREATE TABLE` with its constraints, `DROP COLUMN` or `REFRESH MATERIALIZED VIEW` is one write
  group: it is applied whole or not at all, for a crash, a concurrent reader, a standby and a
  branch.
- **Physical standbys on one connection.** A standby is a read-only physical replica that follows
  its primary over a single replication port. New: `heliosdb-nano standby verify`, online promotion
  with `SELECT pg_promote(wait, wait_seconds)`, `SWITCHOVER TO '<standby>'`, rewinding a former
  primary in place, TLS replication, archived WAL with a recovery window, and synchronous
  replication (`semi-sync` and `sync`).
- **A branch is a fork, selected per session.** `USE BRANCH b` moves only its own session. A branch
  sees its parent as it was at the fork point, has its own catalog for tables, and enforces
  `PRIMARY KEY`, `UNIQUE` and `FOREIGN KEY` over what it sees.
- **No committed write is lost beside a concurrent writer.** Lost increments, duplicate primary
  keys after a rollback, orphaned child rows and racing upserts are fixed; writers now wait for the
  row or key another transaction holds.
- **`AS OF` is correct after fast-path writes and across `DROP COLUMN`.** A one-row `UPDATE` or
  `DELETE` records the row's history in the same write as the row.
- **A long statement no longer stalls the server.** Each statement leaves the network worker that
  serves its connection; primary-key point reads and writes stay on it.
- **Joins under a filter keep their index lookups.** A `WHERE` term on one table no longer turns
  the joins above it into full scans: the 4-table join of the pg35 benchmark is about ten times
  faster, and 4.42.0 is faster than PostgreSQL 18.4 in all 35 of its categories.
- **A reproducible release benchmark and a baseline**, with one command per part, the checksums of
  the binaries measured, a machine-readable copy of every number, and the best time each category
  has reached recorded as its baseline.

## Does 4.42.0 break anything?

Yes, in two areas. Both are labelled BREAKING in the changelog.

| Area | Before 4.42.0 | In 4.42.0 | What to do |
|---|---|---|---|
| Branch selection | `USE BRANCH b` moved every connection of the database | It moves only its own session; a session can also use `SET heliosdb.branch = 'b'`, `dbname=<db>@<branch>` or `options=-c heliosdb.branch=b` | Make each connection select its branch |
| Branch contents | A branch showed its parent's later changes | A branch sees its parent as it was at the fork point | Recreate branches made by an earlier release before merging them; `MERGE BRANCH` refuses them with `55000` for tables whose rows they changed |
| Writes on a branch | Some write paths wrote main | Every write path changes the branch only; what cannot stay on a branch is refused with `0A000` | Run lock-free ingestion, direct bulk load and `CREATE` / `REFRESH MATERIALIZED VIEW` on main |
| Replication | Logical and physical standbys, several ports | Physical standbys only, one connection per standby on `[replication] replication_port` (default 5433), protocol `NPHYS004` | Upgrade the primary and its standbys together and rebuild each standby on a new, empty data directory |
| Writes sent to a standby | Forwarded to the primary | Refused with SQLSTATE `25006` | Connect writers to the primary |
| Removed settings | `--physical-replication-listen`, `[replication.physical] listen`, the observer role, `--observer-hosts`, `HELIOSDB_PRIMARY_PG_PORT` | Removed; an unknown configuration key is an error | Take them out of the configuration before the first start |
| Rust API | `BranchManager::merge_branch`, `run_gc`, `with_gc_config`, `gc_eligible_branches`, `pending_gc_count`, `gc_config`, `BranchGcConfig`, `BranchGcMode` | Removed | `MERGE BRANCH` runs in the engine |

Applications may also notice these changes, which are not labelled breaking:

- A writer waits for a schema statement or `MERGE BRANCH` on its table, up to
  `[session] lock_timeout_ms` (default 30 s), then fails with `55P03`; a deadlock is `40P01`.
- A statement inside a transaction that meets a concurrent schema change fails with `40001`; retry
  the transaction.
- One statement or transaction writes at most about 1.33 GiB of row data, else `54000`; split the
  load into batches.
- `DROP COLUMN` and `SET STORAGE` rewrite a table in one write, up to
  `[storage] max_atomic_rewrite_bytes` (256 MiB), and are refused with `54000` above it.
- A prepared statement whose result columns changed is refused with `0A000` "cached plan must not
  change result type"; prepare it again (asyncpg and pgjdbc do).

## How do I upgrade from HeliosDB-Nano 4.41.x to 4.42.0?

4.42.0 is a drop-in upgrade for a standalone server or a primary that was shut down cleanly. It is
not a drop-in upgrade for standbys. The full procedure is in
[`docs/guides/upgrade.md`](../guides/upgrade.md).

1. Take a `heliosdb-nano dump` of the data directory. A directory that 4.42.0 has written cannot
   be opened by 4.41.x again.
2. Stop the server cleanly, replace the binary and start it:
   `heliosdb-nano stop --pid-file ./heliosdb.pid` (the PID file `start --daemon` wrote; a
   foreground server stops on Ctrl-C or SIGTERM), then `heliosdb-nano start --data-dir ./mydata`.
   Startup no longer replays the logical WAL over committed data.
3. If the start is refused because the directory has log entries above its checkpoint (a 4.41.x
   process that did not shut down cleanly can leave that), stop everything that uses the directory,
   keep the backup, and run
   `heliosdb-nano recover-wal --data-dir ./mydata --adopt-local-state`.
4. Upgrade the standbys in the same maintenance window. Start each one on a new, empty data
   directory; it copies itself from the primary. Keep the old directory until
   `heliosdb-nano standby verify --data-dir …` passes on the stopped new standby.
5. Point each standby's `--primary-host` at the primary's replication port (default 5433), and
   plan disk space for the WAL archive: a node with a replication role archives its WAL to
   `<data dir>.archive` with a 7-day window by default.

Building from source needs Rust 1.88 or later (1.92 with `--features code-embed`). The Linux
release binaries need glibc 2.39 or newer; `scripts/install.sh` now checks that the downloaded
binary starts before it installs it.

## Replication and high availability

- **Verify a standby.** `heliosdb-nano standby verify` proves that a stopped physical standby is
  byte-identical to its primary, by SHA-256 over the replicated keyspace. It exits 0 when
  identical, 1 with every differing key range, and 2 when it could not verify.
- **Promote online.** `SELECT pg_promote(wait, wait_seconds)` promotes a standby while it runs.
  Promotion fences the old primary and moves the dataset to the next epoch, so there are never two
  writable primaries.
- **Switch over.** `SWITCHOVER TO '<standby>'` on the primary's PostgreSQL port (superuser) promotes
  the standby and demotes the primary in place; `SWITCHOVER CHECK TO '<standby>'` reports every
  check and changes nothing.
- **Rewind a former primary.** `recover --from-primary` on a fenced or superseded primary's
  directory rewinds it in place instead of making a full copy.
- **Synchronous replication.** A commit waits until `[replication] min_acks` standbys (default 1)
  acknowledge it: `semi-sync` means durable on that many standbys, `sync` means applied.
  `[replication] sync_timeout_ms` (default 10000) bounds the wait.
- **TLS and resumable copies.** Replication can run over TLS, and without TLS the replication port
  stays on loopback. An interrupted bootstrap copy resumes.
- **Archived WAL.** A node with a replication role archives its WAL; a standby that was away while
  its primary pruned WAL catches up from the archive, and `recover` can rebuild a standby from the
  archive or from the primary.
- **Clear standby states.** A standby that cannot follow (`HistoryMismatch`, `Gap`, `WalPruned`,
  `EpochStale`, `Version`) enters `needs_recovery`: it stays up and refuses data reads with
  SQLSTATE `55000` naming the reason.

Operating a standby, promotion and switchover: [`docs/guides/physical-standby.md`](../guides/physical-standby.md).

## Branching

- `USE BRANCH b`, `SET heliosdb.branch = 'b'`, `dbname=<db>@<branch>` at PostgreSQL startup and the
  REST `/v1/branches/:name/…` routes select a branch for one session.
- A session bound to a branch that was dropped or merged is refused with `3D000` until it selects
  another; switching branches inside a transaction is refused with `25001`.
- Explicit transactions work on a branch, and writers on a branch lock their rows. Before, six
  clients incrementing one row of a branch lost up to 81% of the increments with no error.
- `MERGE BRANCH` carries schema changes, lands through the target's ordinary commit and finishes
  after a crash. `MERGE BRANCH x ABORT` abandons a pending merge and lists what may be partial.
- `MERGE BRANCH` is still last-writer-wins: it has no conflict detection for rows both sides
  changed. It refuses, leaving the source active, with `55000`, `23505`, `55006` or `54000` when
  it cannot land safely.
- Views, materialized views, functions, procedures and sequences are shared by all branches.

## Statement atomicity and schema changes

- A multi-clause `ALTER TABLE` is refused before anything is written if any clause fails. Before,
  `ADD COLUMN c INT DEFAULT 1 CHECK (c > 5)` failed with `23514` and left column `c` behind.
- `CREATE TABLE` (with its constraints), `DROP TABLE` (with its partition children),
  `RENAME TO`, `RENAME COLUMN`, `CREATE INDEX`, `DROP INDEX`, `ADD CONSTRAINT`, `DROP CONSTRAINT`,
  `CREATE`/`DROP VIEW`, `FUNCTION`, `PROCEDURE`, `TRIGGER` and `SEQUENCE` statements are each one
  write group.
- `CREATE MATERIALIZED VIEW` and every form of `REFRESH MATERIALIZED VIEW` populate atomically:
  readers see the old contents or the new, never a mix.
- A new index is invisible to queries until it is complete.
- `ADD COLUMN` with a stable default rewrites no row.
- A statement reads its catalog and its rows under one view. A statement that meets a concurrent
  schema change is planned again, for at most 100 ms, or fails with `40001`.
- `EXPLAIN ANALYZE TRUNCATE` is refused with `0A000`; it used to empty the table even inside a
  transaction that rolled back.
- Statement atomicity does not make DDL transactional across `BEGIN` / `ROLLBACK`: a completed
  schema statement can survive the rollback of the block's DML.

## Time travel (`AS OF`)

- A fast-path one-row `UPDATE` or `DELETE` records the row's history and its snapshot in the same
  write group as the row. In 4.41.1 a row deleted on the fast path was missing from `AS OF`
  queries before the delete.
- `AS OF` and transactions across a `DROP COLUMN` read each value under its own column. Before, an
  old row version could show a dropped column's value under the next column's name.
- `AS OF` reaches snapshots older than the newest ones held in memory; they are found through
  their stored records.
- History cannot cross a table rename or a materialized-view shape replacement that discarded it:
  `AS OF` before that point is refused with `0A000`.
- A store that does not use `AS OF`, `VERSIONS BETWEEN` or branches from the past can set
  `[storage] time_travel_enabled = false` and skip the history writes.

## Correctness fixes

- An `UPDATE … SET n = n + 1 WHERE id = k` beside point readers no longer loses increments.
- An open transaction's `DELETE` no longer frees its key: another writer of that key waits, then
  inserts after a commit or fails with `23505` after a rollback, as in PostgreSQL.
- `ON DELETE CASCADE` and `SET NULL` lock the child rows; a child `INSERT` cannot race a parent key
  change or `DELETE` into leaving an orphan.
- `UPDATE` and `ON CONFLICT … DO UPDATE` enforce `ON UPDATE NO ACTION`, `RESTRICT`, `CASCADE`,
  `SET NULL` and `SET DEFAULT`, including composite keys and self-references.
- Two upserts of one new key no longer fail with `23505` or `40001`; the second waits for the first.
- An aggregate's `FILTER (WHERE …)` is applied; it was dropped on every route.
- Two window functions with the same output name return their own values.
- `random()` returns a value in `[0, 1)`, new for every row.
- Correlated `EXISTS`, `NOT EXISTS`, `IN` and scalar subqueries see the active transaction, its
  staged writes and its savepoints.
- Deleting every key under a long common prefix (UUID primary keys) no longer leaves an index node
  that makes a later insert fail.
- Startup no longer replays old `INSERT`, `UPDATE`, `DELETE` or DDL from the logical WAL over rows
  already committed, which could undo a newer update or restore a deleted row.
- `ORDER BY … NULLS FIRST` and `NULLS LAST` are obeyed; the clause used to be ignored. Without
  the clause the order is unchanged: NULLs come first under `ASC` and last under `DESC`, as in
  MySQL and SQLite and the reverse of PostgreSQL's default.
- A grouped query can be ordered by an output alias together with a group key
  (`GROUP BY s.id, s.name ORDER BY app_count DESC, s.name`).
- `x NOT IN (subquery)` returns no row when the subquery holds a NULL, whatever its size; above
  16 values the NULL was ignored.
- `WHERE d > DATE '2024-06-01'`, `TIMESTAMP '…'`, `INTERVAL '…'` and `LIKE … ESCAPE '…'` no longer
  fail with a parse error outside a transaction.
- `setval()` on the sequence of a `SERIAL` column moves the column's generator, and the position
  survives a restart; it used to answer with its argument and change nothing. The generator only
  moves up.
- A `BEFORE INSERT` trigger function that contains an `IF` no longer skips or rewrites every
  inserted row. Such a trigger changes nothing and a warning is logged; drop and re-create
  triggers made by an earlier release.

## Server and protocol

- A long statement no longer stops the server from accepting connections or serving other
  sessions. `HELIOSDB_NANO_STATEMENT_OFFLOAD=off` restores the previous behaviour.
- `INSERT … SELECT` and `CREATE TABLE … AS` with bound parameters work over the extended protocol.
- A PostgreSQL `CancelRequest` is routed to the statement it names.
- `REFRESH`, `DROP` and `ALTER MATERIALIZED VIEW` and `ALTER SEQUENCE` run over the extended
  protocol and REST.
- ErrorResponse frames carry the `V` (non-localized severity) field, as PostgreSQL 9.6 and later
  send.
- `SELECT pg_catalog.set_config('search_path', '', false)`, the line every `pg_dump` opens with,
  is answered: `SELECT set_config('name', 'value', is_local)` as a statement of its own sets what
  `SET` sets.
- `SELECT * FROM current_schema()`, which TypeORM runs at start-up, returns its one row: a scalar
  function call in `FROM` is a one-row relation.
- `COMMENT ON` is accepted, so dumps and migrations that carry comments run through. The comment
  is not stored.
- A role made with `CREATE USER … PASSWORD` (or `CREATE ROLE … LOGIN PASSWORD`) can log in. Until
  now only the account given at start could. The role's password is stored as a SCRAM-SHA-256
  verifier, never as text; `NOLOGIN` and `VALID UNTIL` are honoured at login.
- A database made with `CREATE DATABASE` is still there after a restart and is listed in
  `pg_database`. The name used to be kept in memory only, and an application configured with
  it could not connect after a restart.

## Vector search

- HNSW indexes are built with the configured parameters: `WITH (ef_construction = …)` and
  `[vector] hnsw_ef_construction` now take effect. At the default `ef_construction` of 200 an index
  builds up to about twice as slowly as before.
- Exact-match vector queries find their row: a search over at most 8192 vectors and at most 2M
  vector components is an exact scan.
- Inner-product (`vector_ip_ops`) indexes accept any vectors; a pair with a dot product above 1
  used to panic the insert or search.
- Loading a saved quantized HNSW graph no longer resurrects deleted rows.
- With `--features vector-persist`, each changed row's vector is recorded in the same write group
  as the row, so a crash cannot leave the change out of the index after reopening.
- On encrypted stores the HNSW dump cache no longer writes plaintext vectors; indexes are rebuilt
  from their sealed rows at open.

## Security

- `cargo audit --deny warnings` and `cargo deny check` pass. Five lockfile entries move to patched
  releases: `rustix` 1.1.6 (RUSTSEC-2026-0486), `linux-raw-sys` 0.12.1, `quinn-proto` 0.11.19
  (RUSTSEC-2026-0523, RUSTSEC-2026-0524), `quinn-udp` 0.5.16 (RUSTSEC-2026-0538) and `libz-sys`
  1.1.33 (RUSTSEC-2026-0544). Only `rustix` is compiled into any build.
- One maintenance exception is recorded: RUSTSEC-2026-0543 declares `chrono` unmaintained; it
  reports no vulnerability and lists no patched version. Scope and removal work are in
  [`docs/SECURITY_MAINTENANCE_EXCEPTIONS.md`](../SECURITY_MAINTENANCE_EXCEPTIONS.md).
- The optional `code-embed` feature moves to fastembed 7.5 and no longer pulls webpki-roots 0.26
  (RUSTSEC-2026-0381). Model downloads trust the bundled Mozilla roots, not the OS trust store.
  The default build and the released binaries do not include `code-embed`.

## What is slower than 4.41.1, and why?

- **One-row writes record history.** A one-row `UPDATE` or `DELETE` writes the row, its version and
  its version-index entry, after checking the row's newest version; on disk the commit also writes
  its snapshot record and that record's three index keys. That is seven keys where 4.41.1 wrote
  one, and it is what makes `AS OF` correct after such a write. With
  `[storage] time_travel_enabled = false` the write path is 4.41.1's again.
- **An in-memory database keeps history beyond its newest snapshots.** Past 2,000 snapshots in
  memory, the commit that crosses the limit writes the records of the oldest 1,000, so `AS OF`
  still reaches them: about 5 ms once per 1,000 commits.
- **Every statement does more to be atomic.** Each statement has its own transaction, one write
  group and a consistent view of the table layouts it reads.

During the release, the benchmark gates found regressions that were fixed before shipping; the
changelog lists each with its measured effect (index point reads on the server, `UPDATE` with a
subquery, `DROP TABLE`, per-transaction bookkeeping, joins under a filter).

## Known limits in 4.42.0

- A read through a secondary index, a primary-key range or an `IN` list can see a concurrent
  multi-row statement partly applied around its commit. It never sees uncommitted rows, and a full
  scan sees the statement whole.
- A correlated subquery on the table of its own outer query returns the whole-table result for
  every row when the inner table has an alias and the outer row is named by the table's name, as
  in `SELECT id, (SELECT COUNT(*) FROM acct AS a WHERE a.grp = acct.grp) FROM acct`, unless the
  statement has a bound parameter (then it is evaluated per row). In `JOIN … ON` such a subquery
  matches nothing instead of being refused. Give the outer table the alias instead. The same rule applies to the subquery of an `UPDATE` or `DELETE`
  (`DELETE FROM d WHERE EXISTS (SELECT 1 FROM d AS b WHERE b.k = d.k …)` matches no row): write
  `DELETE FROM d AS x … x.k`. The same is true of 4.41.1.
- `MERGE BRANCH` has no conflict detection for rows both sides changed.
- `CREATE TABLE … AS`, `CREATE SCHEMA` with elements, `DROP TABLE a, b`, roles and grants, and
  `CREATE DATABASE BRANCH` are still more than one write group.
- One statement or transaction writes at most about 1.33 GiB of row data (about 2 GiB with time
  travel off).
- An in-memory database pauses a writer for about 5 ms once per 1,000 commits.
- MySQL wire authentication is trust-only.
- Privileges are not enforced. `GRANT` and `REVOKE` are recorded and can be read back, but every
  connection that authenticates can read and change everything. A role that can log in is a
  full account.
- Roles log in under `scram-sha-256` and `password` authentication. Under `md5` authentication
  and over HTTP only the account given at start can authenticate. A role whose password was set
  by an earlier release cannot log in until `ALTER ROLE … PASSWORD` sets it again.
- A database made with `CREATE DATABASE` is a name to connect by, with its own connection and
  rate limits. Databases do not separate tables: every connection sees the same tables, and
  `current_database()` answers `heliosdb`.
- An index on an expression (`CREATE INDEX … ((payload->>'k'))`) is accepted and recorded, so
  schemas and dumps that contain one load, but it is not maintained and no query uses it: such a
  query scans. `CREATE UNIQUE INDEX` on an expression is refused.
- Without `NULLS FIRST` or `NULLS LAST`, NULLs sort first under `ASC` and last under `DESC`, the
  reverse of PostgreSQL.

## Frequently asked questions

<!-- generated:faq:begin -->
### What is HeliosDB-Nano 4.42.0?

HeliosDB-Nano 4.42.0 is the 2026-11-20 release of HeliosDB-Nano, an Apache-2.0 embedded ACID database in a single binary that speaks the PostgreSQL and MySQL wire protocols. It makes every statement atomic, replaces replication with physical standbys that can be promoted online, and turns a branch into a per-session fork.

### Is HeliosDB-Nano 4.42.0 faster than PostgreSQL?

In the pg35 benchmark, embedded HeliosDB-Nano 4.42.0 is faster than PostgreSQL 18.4 in all 35 SQL categories. HeliosDB-Nano 4.41.1 was slower than PostgreSQL in one of them, the 4-table join. That compares an in-process, in-memory engine with a PostgreSQL server over TCP that syncs every commit; with both engines as servers the margins are much smaller (see the pgbench tables in the release benchmark).

### Is HeliosDB-Nano 4.42.0 faster or slower than 4.41.1?

Both. In pg35, 15 of 35 categories are within 15% of 4.41.1, 6 are faster and 14 are slower. One-row INSERT, UPDATE and DELETE are slower because each commit now records row history; over the wire a one-row UPDATE runs at 0.48–0.74 of 4.41.1's throughput between 1 and 64 clients.

### What is the pg35 baseline, and which categories did 4.42.0 improve?

The pg35 baseline is the best time per statement each of the 35 benchmark categories has reached in a release; a release that reaches a new best sets the baseline for that category. 4.42.0 sets a new baseline in 9 of 35 categories (ALTER TABLE, DROP TABLE, CREATE/DROP VIEW, INSERT..SELECT, UPSERT, INNER JOIN, LEFT JOIN, 4-table JOIN, Transaction ctl). In the other 26 the baseline stays with 4.41.1; 4.42.0 is within 15% of it in 12 and more than 15% slower in 14.

### Why are single-row writes slower in 4.42.0 than in 4.41.1?

Since 4.42.0 a one-row UPDATE or DELETE writes the row, its version and its version-index entry in one write group, and on disk also the commit's snapshot record: seven keys where 4.41.1 wrote one. That is what makes AS OF (time travel) queries correct after such a write; 4.41.1 lost a row deleted on its fast path from AS OF queries before the delete.

### How do I get 4.41.1's write speed back?

If the store does not use AS OF, VERSIONS BETWEEN or branches from the past, set time_travel_enabled = false in the [storage] section of the configuration file. Measured that way, the 4.42.0 server runs a one-row UPDATE at 0.89–0.94 of 4.41.1's throughput at 1, 16 and 64 clients.

### How do I upgrade from HeliosDB-Nano 4.41.x to 4.42.0?

Read docs/guides/upgrade.md first. Standbys must be rebuilt because replication is physical-only in 4.42.0, a data directory last written by an older build is adopted once at first start, and some application-visible behaviour changes (branches are selected per session).

### How can I reproduce the HeliosDB-Nano 4.42.0 benchmarks?

Start PostgreSQL 18.4 in a container, then run benches/public/release_bench.sh v4.41.1 out from a checkout of the release (pg35 plus the wire UPDATE at 1 to 64 clients, about two hours) and docs/benchmarks/bench-engines.sh for pgbench. docs/benchmarks/REPRODUCING.md has the exact commands and how to check the binaries' checksums.

### On what hardware were the benchmarks run?

On one Linux x86_64 host with 32 logical CPUs and at least 64 GiB of memory, with client and server on the same host. Absolute times differ on other hardware; the ratios between the two releases are what should agree.
