# SQLite mirror — HeliosDB-Nano vs SQLite, June 2026

Head-to-head of identical workloads on identical schemas:
`tests/tps_workloads.rs::run_tps_suite` (Nano, embedded, in-memory) vs
`benches/external/sqlite_tps_mirror.py` (SQLite `:memory:`, Python stdlib).
Generated by `benches/public/run_sqlite_mirror.sh`; every number below comes
from that script's output on the host described here. Wins **and** losses are
published.

- Date (UTC): 2026-06-11
- Engine commit: `e129247` (v3.48.0 integration merge; the D5 branch only
  touches the test harness and benches, not engine code)
- Host: AMD EPYC 7371 16-Core (32 logical cores), 126 GiB RAM,
  Linux 5.14.0-611 (el9), xfs on md-RAID
- rustc 1.95.0; Python 3.9.25 with stdlib SQLite **3.34.1** (the el9 system
  build, 2021 vintage — a newer SQLite may do somewhat better)

## Methodology — read before quoting

- **Single-threaded by construction.** Both harnesses are ONE client issuing
  ONE statement at a time. These are per-statement engine latency numbers,
  not multi-client throughput. For concurrency see
  `benches/public/run_concurrency.sh`.
- **No durability on either side** (Nano in-memory / SQLite `:memory:`) —
  this isolates the CPU path. For durable writes at honest fsync tiers see
  `docs/benchmarks/DURABLE_WRITES_2026_06.md`.
- **Binding styles.** The Nano harness interpolates literal SQL.
  `bindings=literal` makes SQLite execute the same statement text
  (apples-to-apples: both engines re-parse every statement).
  `bindings=params` is SQLite's best embedded shape (prepared statement
  cache); it is published too because real SQLite applications use it.
- **Result-cache disclosure.** The Nano harness appends a marker that
  bypasses Nano's result cache on the scan/aggregate/join workloads, so
  repeated identical scans measure the operator path, not a cache hit.
  SQLite has no result cache.
- N = table rows (`users`; `orders` gets 2N), M = single-op statements per
  point workload, scans/aggregates run 20 iterations and joins 10.

Repro:

```bash
benches/public/run_sqlite_mirror.sh          # both scales, both binding styles
```

## The headline question: did the v3.38→v3.48 analytics work flip large-N?

**Partially — aggregation flipped decisively, scans/join/top-N did not.**

- `agg_count_sum_avg` at 200k: **3.78x faster than SQLite** (was a loss at
  this scale before the parallel-aggregation work; it is still 0.51x at 10k
  where the parallel path doesn't pay for itself).
- `group_by_status` at 200k (400k-row orders table): **16.1x faster**
  (8.9 ms vs 143 ms per query).
- `filter_scan(age>50)` still loses (~0.5x at both scales). The predicate
  matches ~45% of rows, so zone-map pruning cannot help and per-row
  materialization of the result set dominates.
- `join_users_orders` still loses at both scales (0.42x / 0.33x) — the join
  path remains Nano's weakest shape against SQLite's nested-loop over a
  covering rowid lookup.
- `order_by_limit10` (top-N) is the worst large-N loss (0.08x): 175 ms vs
  13.7 ms per query over 200k rows. SQLite scans+heaps in C; Nano's top-N at
Diagnosed post-publication: top-N scales linearly with N (O(N log k) is engaged); the deficit is row-decode SCAN RATE (~1.6M rows/s vs SQLite's ~15M on this shape) — the known row-materialization gap, addressed by the typed-batch roadmap item (R3.4). Optimization target.

## Honest notes

1. **The M=40 cliff at N=200k.** With only 40 single-op statements right
   after a 600k-row bulk load, first-op warmup dominates the three † rows.
   Cross-check, same suite at N=200,000 / M=2,000 (measured on the same host,
   same day): autocommit_insert 33,615 ops/s, point_lookup_pk 148,273 ops/s,
   update_by_pk 134,300 ops/s. Even with that correction: cold point lookups
   at 200k are ~2x slower than at 10k (317k → 148k ops/s) while SQLite barely
   degrades, and autocommit INSERT drops 3.7x (122k → 33.6k ops/s) — a real
   scale-sensitivity gap on the write and cold-read paths, not just an
   artifact.
2. **Bound parameters.** SQLite with prepared statements is ~3.5x faster
   than Nano's literal-SQL harness on bulk ingest (456-512k vs 142-165k
   ops/s). Nano's own parameterized path (`run_param_tps_suite`, N=10k,
   measured same host/day: param_bulk_insert 189k, param_execute_many_insert
   243k, param_point_lookup_pk 297k ops/s) closes the lookup gap to parity
   but still trails SQLite's params bulk ingest by ~2x.
3. **Old SQLite.** 3.34.1 (el9 stdlib). Treat SQLite's columns as a floor,
   not a ceiling.
4. **Single run per scale.** These are not averaged; spot reruns moved
   point numbers by ±10% and the conclusions not at all (raw logs of every
   run are kept under `benches/public/results/`).
