# Public, reproducible benchmarks (roadmap item D5)

One-command, no-fabricated-numbers benchmark scripts. Every script:

1. checks its dependencies (cargo, rustc, python3, git — nothing else; the
   SQLite side uses Python's stdlib `sqlite3`),
2. builds the harness (`cargo test --profile perf --test tps_workloads --no-run`),
3. runs the workloads, and
4. writes a timestamped results directory under `benches/public/results/`
   (gitignored) containing raw logs, a commit/host-stamped `results.json`,
   and a human-readable `RESULTS.md`.

Published numbers live in `docs/benchmarks/` and must come from one of these
scripts' output — never hand-edited. Honesty rules baked in:

- **Single-threaded disclosure.** The TPS suite and the SQLite mirror are one
  client issuing one statement at a time. They measure per-statement engine
  latency, not concurrent throughput. Multi-threaded numbers come only from
  `run_concurrency.sh` / the durable scaling bench, and say so.
- **Durability-tier disclosure.** Write numbers are only comparable within the
  same durability tier (see `run_durable_writes.sh` header). Comparing a
  non-fsync number against an fsync number is the dishonest-multiplier trap.
- **Losses are published too**, with raw logs attached.

## Scripts

| script | what it measures |
|---|---|
| `run_sqlite_mirror.sh` | HeliosDB-Nano vs SQLite, identical workloads/schema (`tests/tps_workloads.rs::run_tps_suite` vs `benches/external/sqlite_tps_mirror.py`), in-memory, two scales (N=10000/M=2000 and N=200000/M=40), both SQLite binding styles. `--quick` = small scale only. |
| `run_durable_writes.sh` | The Durable Writes Gauntlet: write workloads at honest durability tiers — Nano `durable_commit=true` vs SQLite `synchronous=FULL` (Tier 1), Nano disk default vs SQLite WAL/NORMAL (Tier 2) — plus Nano multi-session durable commit scaling (`run_durable_commit_bench`). |
| `run_concurrency.sh` | Multi-threaded embedded benches: hot-row lookups at 1/4/16 threads (`run_cache_concurrency_bench`), per-session transaction cycles (`run_session_txn_bench`, R0.1), and write-write conflict detection with zero-lost-update assertion (`run_conflict_bench`, R0.2). |
| `ci_perf_smoke.sh` | The CI perf gate (used by `.github/workflows/perf-gate.yml`): TPS suite at N=1000/M=200 + the in-txn FK bulk-insert shape, best-of-3, checked against `ci_baseline.json`. |
| `regen_ci_baseline.sh` | Regenerates `ci_baseline.json` from a fresh run on the current machine (rates pre-scaled down, default 0.5x). |
| `bench_tools.py` | Shared stdlib-only tooling: `parse` (bench text → JSON), `assemble` (stamped results.json), `check` (gate), `baseline` (generate), `compare` (markdown tables). |

Env knobs are documented in each script's header. Useful extras:

- `HELIOS_TPS_PERCENTILES=1` — the TPS suite times every single-op statement
  individually and appends p50/p95/p99 to the per-op workload lines. Leave it
  OFF for cross-engine/baseline ops/s comparisons (per-op timing adds ~tens of
  ns per op).
- `SCALES="50000:10000"` — custom `N:M` pairs for `run_sqlite_mirror.sh`.

## The CI perf gate

`.github/workflows/perf-gate.yml` runs `ci_perf_smoke.sh` on every PR and on
pushes to `main` that touch engine code. Design:

- **Workloads:** the 11-workload mem TPS suite at N=1000/M=200, plus
  `run_fk_bulk_insert_bench` (2000 FK-bearing INSERTs inside one transaction —
  the exact shape of the v3.28.0 338x FK regression that shipped ~2 weeks
  undetected). Total runtime is seconds once the build cache is warm.
- **Noise handling:** each workload's score is the best of 3 runs; the
  baseline was generated on a workstation and pre-scaled by 0.5x; the gate
  fails only when measured < baseline / 2.5. Net effect: a workload must be
  roughly **5x slower than the baseline machine** to fail. This catches the
  10x-338x cliff class, deliberately not 20% drift.
- **Baseline:** `benches/public/ci_baseline.json` (committed). The first CI
  run on new runner hardware may fail across the board — that means the
  baseline needs a refresh from that hardware class, not that the engine
  regressed. Regenerate with `benches/public/regen_ci_baseline.sh` and commit
  the diff with an explanation. Never regenerate to silence a failure you
  cannot explain; a single-workload failure at a large factor is a real
  regression.
