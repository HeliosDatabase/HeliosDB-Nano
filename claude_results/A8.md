# A8 Result — Connection recovery after constraint errors

## Verdict

Positive. Commit eligible. **Real bug found and fixed on the extended-query path.**

This converged with Codex's finding. My first pass mis-verdicted A8 as "already
fixed" because I tested only the **simple-query** path (`batch_execute` /
`simple_query`) and the acceptor semaphore — both of which are genuinely sound
at `37238cc`. Codex's run surfaced the real gap on the **extended-query** path
(`tokio_postgres::execute`, the path asyncpg/psycopg/tokio-postgres use): an
Execute-time constraint error sent `ReadyForQuery` *before* the client's `Sync`,
which closes/wedges the driver connection. After confirming the gap reproduces
in my own checkout, I **ported Codex's fix** (it is the minimal, correct,
PostgreSQL-shaped recovery) and kept my broader test set.

Root-cause credit: Codex (`fix/codex-v334-deficiencies`, commit `6d16cf1`).

## Fix

Add an `awaiting_sync_after_error` connection state. When a Parse/Bind/Execute/
Describe/Close message errors, send `ErrorResponse` (and flush) without an early
`ReadyForQuery`, then discard frontend messages until the client's `Sync`, at
which point `ReadyForQuery` is sent. `send_error` is split into
`send_error_message` (ErrorResponse only) + `send_error` (adds RFQ for the
simple path). This is byte-for-byte the recovery Codex implemented.
