## What I got wrong, and the catch

I correctly found that `ArtIndexManager::encode_key` uses the full `s.as_bytes()`
(no ~100-char truncation), and my 2-row test (two values sharing a 150-char
prefix) passed. **But the real bug needs many long-shared-prefix keys** to
trigger ART node path-compression + split past `MAX_PREFIX_LEN`. Codex's wider
baseline (100 distinct UNIQUE TEXT values, same 100-char prefix, suffixes
000..099) failed at **insert 20** with a false duplicate-key error.

Independently reproduced on `6566104`: 100 `execute_params` inserts of distinct
`prefix+NNN` tokens → `Duplicate key ... UNIQUE constraint "token"` at insert 20.

## Root cause

`src/storage/art_index.rs`: ART inner nodes store only the first `MAX_PREFIX_LEN`
bytes of a compressed prefix while keeping the full `prefix_len`. Insert compared
only the *stored* prefix bytes and then skipped the full `prefix_len`. When the
real mismatch lay in the hidden prefix tail, the key routed to the wrong child
and could collide with a distinct key — a false UNIQUE duplicate. `encode_key`
was a red herring.

## Fix (Codex `0254bd2`, integrated)

Compare the hidden compressed-prefix tail against a representative descendant
leaf key before treating the full prefix as matched (`prefix_mismatch_pos` +
`first_leaf_key`); when splitting past `MAX_PREFIX_LEN`, recover the hidden bytes
from that leaf (`prefix_bytes_for_split` / `prefix_byte_for_split`); apply the
same full-prefix check in get/get_all/remove/remove_value. `encode_key`
unchanged.
