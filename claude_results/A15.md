# A15 Result — asyncpg binary int4 mis-decode inside transactions

## Verdict

Positive. Commit eligible. **Real bug, fixed.** Root cause is NOT the checklist's
"Bind frame-length offset" — it is the extended-query RESULT path ignoring the
client's binary result-format request.

Baseline: this item was started from the consolidated final-main baseline
(`final/main` = `ddb651b`, A8 + reconciled A14), on branch `fix/claude-v334-a15`.

## Root cause

`asyncpg` (and `tokio_postgres`) are binary-first: they request binary result
formats in Bind and decode DataRow columns as binary. The extended Execute path
emitted every DataRow value via `tuple_to_pg_values`, which encodes **text only**
(`Value::Int4(1)` -> ASCII `"1"`, 1 byte), ignoring `portal.result_formats`. A
binary int4 decode expects 4 bytes, sees 1 -> `insufficient data in buffer:
requested 4 remaining 1` (the "1" == a single-digit value). The Describe path
also hardcodes `format_code: 0`.

The checklist's "frame-length read from wrong offset in Bind" is a misdiagnosis:
`parse_bind` advances its cursor correctly; the failure is on result encoding.

## Fix (`src/protocol/postgres/`)

- `handler.rs`: extracted the existing per-value text encoder into
  `value_to_pg_text`; added `value_to_pg_binary` (PG binary wire format for the
  fixed-width scalars: bool, int2/4/8, float4/8, plus text/bytea/uuid), a
  `result_format_is_binary` helper (0 codes = all text, 1 code = applies to all,
  N codes = per column), and `tuple_to_pg_values_with_formats`.
- `handler_extended.rs`: capture `portal.result_formats` and route all three
  DataRow encode sites (catalog SELECT, regular SELECT, DML RETURNING) through
  `tuple_to_pg_values_with_formats`.
- Types without a binary encoder yet (numeric, JSON, temporal, arrays/vectors)
  fall back to text. A client requesting binary for those would still mis-decode,
  but that equals the prior always-text behaviour and is out of the int4 scope.

Note: most of the `handler.rs` line delta is mechanical re-indentation from
extracting `value_to_pg_text` out of the closure; the net new logic is ~60 lines.

## Harness finding (separate, pre-existing — flagged)

The in-process `PgServer` test harness **stack-overflows on _parameterized_
extended queries** (e.g. `INSERT ... VALUES ($1,$2)`), even with a 32 MB worker
stack. A8/A14 extended tests avoided it (no `$N`). This is a harness artifact,
not a server bug: an out-of-process daemon is unaffected (the user's asyncpg
repro produced a *decode error*, not a server crash; cf. the `#[ignore]`'d tests
in `tests/extended_query_param_select.rs` "verified externally"). Consequence:
binary int4 *parameter INPUT* could not be wire-tested in-process. Int4 param
decode is already implemented (`decode_binary_parameter`, OID 23) and was not the
failing surface. The A15 test therefore uses a no-parameter SELECT, which still
forces a binary int4 RESULT decode.
