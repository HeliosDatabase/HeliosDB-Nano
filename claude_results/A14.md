# A14 Result — "Transaction already active" fires spuriously on BEGIN

## Verdict

Positive. Commit eligible. **Real bug, fixed on BOTH the simple-query and
extended-query paths.**

Acceptance (checklist): after any error response, the client must be able to
send BEGIN and start a fresh transaction without a spurious "Transaction
already active" error, with the connection still usable.

## Root cause

Two distinct desyncs between the handler's `transaction_status` and the engine's
actual transaction state:

1. **Simple path**: a query error inside a transaction sets
   `transaction_status = Failed` (handler.rs `send_error_for_query`) but does NOT
   roll back the engine transaction. A follow-up `BEGIN` (status `Failed`, not
   `InTransaction`) falls into the `else` branch and calls `self.database.begin()`
   while the engine still holds the aborted transaction → `"Transaction already
   active"` (lib.rs begin_transaction).
2. **Extended path**: `handle_execute_extended` runs `BEGIN`/`COMMIT`/`ROLLBACK`
   and DML *all* through `self.database.execute_params(...)` and never updates
   `transaction_status`. So the handler state machine (and the simple-path
   recovery) is bypassed entirely; after an aborted transaction the engine txn
   stays active and the next extended `BEGIN` hits the same "already active".

## Fix (minimal, protocol-handler scope)

- `handler.rs` BEGIN branch: if `transaction_status == Failed`, roll back the
  aborted engine transaction and reset to `Idle` before `db.begin()`, so BEGIN
  starts a fresh transaction instead of erroring.
- `handler_extended.rs` `handle_execute_extended`: detect transaction-control
  statements (`BEGIN` / `START TRANSACTION` / `COMMIT` / `ROLLBACK`) and route
  them through the shared `handle_single_query` state machine with
  `suppress_ready_for_query` set (the extended protocol emits ReadyForQuery only
  after `Sync`). This unifies transaction-state tracking across both protocols
  and makes the in-txn error correctly mark the connection `Failed`.
- Visibility: widened `handle_single_query` and the `suppress_ready_for_query`
  field to `pub(super)` (matching the existing `pub(super)` pattern for
  `database` / `prepared_statements` / `send_message`).

Note: this makes `BEGIN`-after-aborted-transaction *start a fresh transaction*
(rollback + begin), which is what the checklist acceptance requires. Strict
PostgreSQL would instead warn and keep the aborted transaction until ROLLBACK;
the pragmatic behavior here prevents the documented connection wedge.
