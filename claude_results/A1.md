# A1 Result — `WHERE col = ANY($array)` returns 0 rows

## Verdict

**REAL BUG — fixed** (confined-marker approach, Codex `9dc5d28`).

Baseline: branch from consolidated `final/main` `e32d58d` (A8+A14+A15+A5).

## Root cause

`src/sql/planner.rs` `Expr::AnyOp` only rewrote a literal regtype-cast array
(`'{int}'::regtype[]`) into an `InList`. A **bound array parameter** (`$1`) and an
**array constructor** (`ANY(ARRAY[...])`) both failed `literal_array_to_list` and
fell through to `Literal(Boolean(false))` — a constant-false predicate that
matches nothing regardless of the bound value, so the query silently returned 0
rows.

Independently reproduced (RED): `query_params("... WHERE name = ANY($1)", [Array(['alice','carol'])])`
returned 0 rows (expected 2).

## Two designs compared (the useful part of this item)

- **Claude (not integrated):** planner emits `InList{[param]}` and rewrites
  `ARRAY[...]` elements into the list; the evaluator **globally** expands any
  array-valued `InList` item. Simple, fixes A1 — **but I verified it also changes
  `IN ($1)` with an array param (0 → 2 rows)** and `IN (ARRAY[...])`, an
  unrequested semantic change to plain `IN`.
- **Codex (integrated, `9dc5d28`):** planner rewrites literal/`ARRAY[...]` arrays
  to a plain `InList`, and a parameter array to an `InList` carrying an internal
  `__hdb_any_array` marker (a `ScalarFunction`); the evaluator expands **only**
  that marker (and errors if the bound value isn't an array). `IN` semantics are
  untouched.

## Decision

Integrated Codex's confined version — it avoids the `IN ($1)` semantic change.
I discovered that side-effect in my own approach; Codex then **ported my finding
as a guard test** (`a1_plain_in_parameter_array_is_not_rewritten_as_any`: plain
`IN ($1)` with an array param must NOT expand like `ANY`). Net: my naive impl
surfaced the trap, Codex's design + my guard test lock in the correct behavior.

## Tests (`tests/v334_a1_any_param_array.rs`, Codex union + my guard)

`ANY($1)` (text), `ANY($1::text[])`, `ANY(ARRAY[...])`, the old
`'{...}'::regtype[]` cast form, an int-array stress loop, and the `IN ($1)`
non-expansion guard.

## Follow-ups (out of A1 scope)

- `col = ANY(<column>)` / `ANY(<subquery>)` (true array columns) still fall back
  to constant-false (no execution-time array operator) — unchanged.
- `col <> ALL($array)` (the NOT-IN array idiom) currently errors (no `AllOp`
  planner arm). It is not a silent-wrong-result, so out of A1's scope — candidate
  for its own item.
