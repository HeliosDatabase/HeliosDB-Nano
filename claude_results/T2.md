# T2 Result — COUNT(*) over a materialized view returns 0 (CORRECTED)

## Verdict

**REAL BUG — fixed** (Codex's 4-site fallible version integrated).

## Both attempts + the catch

Both agents found the same root cause: storage fast paths counted the
user-visible MV name, but MV rows live under `__mv_<name>`, so the count targeted
a non-existent table and returned 0 (while `SUM(1)`/scan resolved the name).

- **Claude (two sites):** fixed `COUNT(*)` direct + single-PK count. Meets the
  checklist's `COUNT(*)` acceptance — **but I verified it still leaves
  `COUNT(id) FROM mv` = 0** (got `COUNT(*)=3, COUNT(id)=0, SUM(1)=3`), because
  column-aggregate pushdown (columnar + row-store) also scans the logical MV
  name. My implementation also used `view_exists(...).unwrap_or(false)`, which
  swallows catalog-read errors.
- **Codex (integrated, `1111f0e`):** a single fallible
  `Executor::fast_path_storage_table_name()` applied at **all four** storage fast
  paths — `COUNT(*)` direct, single-PK count cardinality, columnar aggregate
  pushdown, row-store aggregate pushdown — and it preserves the missing-backing-
  table error rather than silently treating it as "not an MV".

My "did you resolve both count sites?" comparison prompt is what led Codex to
probe further and find the `COUNT(id)` / column-aggregate hole. Net: my prompt
surfaced the gap; Codex's design closed all four paths correctly.

## Decision

Integrated Codex's complete 4-site fallible fix. My two-site version is
superseded (it would have shipped `COUNT(id) FROM mv` still broken).
