## What I got wrong, and the catch

My first A5 pass tested via `db.execute()` (simple-query SQL). That path already
enforced CHECK, so my 3 tests were green and I concluded "already fixed". **Codex
caught that this only covered one path.** The **parameterized** write path
(`execute_params` / `execute_plan_with_params` — used by every real driver via
the extended/prepared protocol) did **not** enforce CHECK.

Same lesson as A8: test the real client path. I independently reproduced on the
baseline (`49cbd39`):
`execute_params("INSERT INTO t(id,balance) VALUES ($1,$2)", [1, -50])` against
`balance INT CHECK (balance >= 0)` returned **Ok(1)** and the negative row
**persisted** — a silent CHECK bypass.

Codex's expanded baseline failed 0/4 before the fix: parameterized INSERT,
parameterized UPDATE (inline + table-level CHECK), and ON CONFLICT DO UPDATE all
accepted CHECK-violating tuples.

## Fix (Codex `20cbf89`, integrated)

`src/lib.rs` (+26): a `validate_check_constraints` helper (loops
`table_constraints.check_constraints`, calls the existing
`evaluate_check_constraint`, errors with the same message as the slow path),
called from the four parameterized write sites — INSERT, INSERT…SELECT,
ON CONFLICT DO UPDATE (after assignments), and UPDATE (before storage write). No
parser/catalog/storage/protocol changes.
