# T8 Result — GROUP BY without aggregates does not dedupe

## Verdict

**REAL BUG — fixed.** (Was "unconfirmed" in my triage.) The root cause is more
general than the checklist's MV framing.

Baseline: branch `fix/claude-v334-t8` from consolidated `final/main` `51591d2`.

## Root cause (general, not MV-specific)

The checklist frames this as a materialized-view materialization bug, but the
defect is in the planner for **all** queries:
`src/sql/planner.rs` builds the GROUP BY / aggregate plan only when
`has_aggregates` is true (`!aggr_exprs.is_empty()`). When a query has a GROUP BY
but **no aggregate functions**, it took the `else` branch and added a plain
projection — **silently dropping the GROUP BY** and returning every base row.

Reproduced directly (no MV): `SELECT a, b FROM t GROUP BY a, b` over 6 rows with
3 distinct (a,b) pairs returned **6** rows (`SELECT DISTINCT a, b` returned 3).
The MV simply inherited this because it materializes the same defining query.

## Fix

`src/sql/planner.rs` (+12/−1): also route GROUP-BY-without-aggregates through the
aggregate path (`if has_aggregates || has_group_by`), with empty `aggr_exprs`, so
the grouped operator dedupes by the group key and the projection maps
`group_N` columns. This is deliberately **not** a blanket `DISTINCT` on the
projection — `SELECT a FROM t GROUP BY a, b` must emit one row per (a, b) group,
which the aggregate path produces correctly (verified: returns 3, not
`COUNT(DISTINCT a)`).

## Baseline (before) → After

- Direct `SELECT a,b FROM t GROUP BY a,b`: **6 → 3**.
- `SELECT a FROM t GROUP BY a,b`: one row per (a,b) group = 3 (correct).
- MV `CREATE MATERIALIZED VIEW mv AS SELECT a,b FROM t GROUP BY a,b`: scan and
  `COUNT(*)` both **6 → 3**; rows are exactly the distinct pairs.
