# A4 Result — binary TIMESTAMP / UUID parameter inputs (CONVERGED)

## Verdict

**REAL BUG — fixed** (Codex's exact-length `1114|1184` + `2950` decoder
integrated; Claude's offset conversion + pure-decoder test unioned).

## Root cause

`decode_binary_parameter` (`src/protocol/postgres/prepared.rs`) handled a fixed
OID set and fell through to `Value::Bytes` otherwise, so binary-mode TIMESTAMP
(OID 1114) and UUID (OID 2950) — psycopg3's default — decoded to `Value::Bytes`
and later failed to cast.

## Both attempts → integrated version

- **Claude:** added `1114` (8-byte BE i64 µs since the 2000-01-01 PG epoch →
  `Value::Timestamp` via `from_timestamp_micros`, checked offset) and `2950`
  (16-byte → `Value::Uuid`). Length-guarded with `get(0..N)/try_into`.
- **Codex (integrated, `15ce31c`):** same conversion (it ported mine) but
  **stricter**: `1114 | 1184` (also `timestamptz`, identical wire format) and
  `2950` with **exact-length** checks (`data.len() != 8` / `!= 16`), so an
  overlong 9-byte timestamp or 17-byte UUID is a protocol error. My `get(0..N)`
  would silently accept overlong payloads — Codex's exact check is the more
  correct PG behaviour.

## Decision

Integrated Codex's exact-length `1114|1184`/`2950` decoder + Codex's
extended-protocol guard/stress tests, plus my focused pure-decoder regression
(`tests/v334_a4_binary_ts_uuid_params.rs`). My `timestamptz`-union and offset
suggestions were both adopted.

## Tests (union)

- `tests/postgres_extended_protocol_tests.rs` (Codex): decoder filter incl
  TIMESTAMPTZ 1184, malformed short/long → protocol error, i64 MIN/MAX range
  errors, 10k timestamp+uuid stress (~3.7 ms).
- `tests/v334_a4_binary_ts_uuid_params.rs` (Claude): `decode_parameter(_, 1, 1114)`
  at epoch + 1 day; `decode_parameter(_, 1, 2950)` UUID round-trip.
